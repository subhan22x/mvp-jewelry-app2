# Adversarial review — static thumbnail pipeline plan

Lens: clean-checkout/bootstrap, generated-file imports, webpack/HMR, dev/build entrypoints, watcher lifecycle, locking, atomic manifest publication, pruning, deterministic hashing, immutable caching/rolling deploys, serverless tracing, manifest scale.

Method: read-only inspection of `docs/plans/static-thumbnail-pipeline.md`, `package.json`, `next.config.mjs`, `run.sh`, `playwright.config.ts`, `.gitignore`, config/data/asset sources, and the picker/component call sites. I did not run builds, inspect `.env`, or measure bytes with a shell (no Bash tool). Baseline "10.9 MiB" is taken from the prompt.

## Findings

### P1 — Gitignored generated manifest is imported by app code; clean checkout breaks tests/typecheck/dev before any generator runs

Plan sections: §2 (line 107–108: "Ignore generated derivatives, **manifest**, temporary files, and local cache in Git") and §4 (line 122–124: only `npm run build` and "the development launcher" generate).

Verified evidence:
- `package.json:6` `"dev": "next dev"`, `:11` `"test": "vitest run"` — neither generates anything.
- `playwright.config.ts:9` webServer runs `npm run dev`.
- `run.sh:140` bypasses npm hooks: `exec npx next dev -p "$PORT"`.
- `app/name/__tests__/nameBuilder.test.tsx:5` imports `NameBuilder`; `app/name/NameBuilder.tsx:7` imports `ThemedImageOption`; the plan says `StaticThumbnail` resolves asset IDs "through the generated browser manifest" (§Browser component), so the manifest becomes a transitive import of the tested component tree.

Failure scenario: fresh clone → `npm ci && npm test` → Vite "Failed to resolve import …/manifest.generated.json"; `npx tsc --noEmit` and `npm run dev` likewise fail with module-not-found because the file is neither committed nor generated by those entrypoints.

Correction: either commit a deterministic `manifest.generated.json` (it is content-addressed and small) and add `thumbnails:check` that fails when it drifts from the catalog, or guarantee generation via npm `predev`/`pretest`/`prebuild`. Committing removes an entire class of bootstrap failures; keep derivatives gitignored.

Acceptance test: fresh clone, no manual step: `npm ci && npm test`, `npx tsc --noEmit`, `npx playwright test` all pass; `npm run thumbnails:check` fails if the committed manifest is stale.

### P1 — Plan hooks a single "development launcher," but there are four independent dev/build entrypoints

Plan section: §4 line 122–125 ("The development launcher generates the initial manifest before starting Next…").

Verified evidence: `package.json:6` (`npm run dev`), `run.sh:140` (`npx next dev`, used by documented `./run.sh` in `README.md:97-101`), `playwright.config.ts:9` (`npm run dev -- --port 3001`), `render.yaml:6` and Vercel (`docs/vercel-deployment.md:17`, build command `npm run build`). No `pre*` scripts exist in `package.json:5-31`.

Failure scenario: generation is wired only into `run.sh` → Playwright and `npm run dev` start Next without a manifest and fail at import; generation wired only into `build` → all dev/test paths fail. Because `run.sh` calls `npx next dev` directly, even adding `"predev"` to npm does not cover it.

Correction: one idempotent `npm run thumbnails`; invoke from `predev` + `prebuild` (and `pretest` if the manifest isn’t committed); change `run.sh` to `npm run dev -- -p "$PORT"` (preserving Prisma Studio handling). Playwright then inherits `predev` unchanged.

Acceptance test: a scripted matrix runs generation through `npm run dev`, `./run.sh`, Playwright webServer, and `npm run build`, each from a state with no `public/thumbnails` and no manifest, and each reaches a serving dev server / successful build.

### P1 — Generator uses a devDependency TypeScript runner (`tsx`), which can be absent in production builds

Plan section: §2 line 96–97 ("using the installed Sharp dependency and TypeScript runner").

Verified evidence: `package.json:54` `sharp` is a dependency, but `:84` `tsx` and `:85` `typescript` are devDependencies. `render.yaml:6` builds with `npm ci && …`; `README.md:150` documents Render as supported. The repo already has a precedent for avoiding `tsx` in prod scripts: `package.json:24` uses `node --experimental-strip-types` for `r2:migrate-generated`.

Failure scenario: `NODE_ENV=production npm ci` (or any `--omit=dev` install) drops `tsx`; the build command `npm run build` → `npm run thumbnails` → `tsx: not found`, so Render/preview pipelines fail even though `sharp` is present. `thumbnails:check` is also unusable in a production container.

Correction: implement the generator as a plain `.mjs` (or Node type-stripped) script importing only `sharp`; keep types in `.d.ts`/JSDoc if desired. Do not make CI correctness depend on devDependencies.

Acceptance test: `npm ci --omit=dev && npm run thumbnails` and `… && npm run build` succeed.

### P2 — Writer lock scope is undefined; a long-lived dev watcher can deadlock a build

Plan section: §2 line 105 ("Use a single writer lock for concurrent dev/build invocations").

Failure scenario (hypothesis grounded in the plan’s own watcher requirement in §4): if the lock is acquired for the watcher process lifetime, `npm run build` (or a second `run.sh`) blocks indefinitely or fails; if it is acquired per-pass, concurrent passes can still interleave with the watcher’s debounced pass. Neither scope is stated.

Correction: lock only the critical section (read catalog → write temp derivatives → `rename` manifest), with a bounded wait and stale-holder detection (PID + mtime). The watcher must release between passes. Builds use a short timeout with an actionable error. Watcher/index/temporary files must be excluded from locking.

Acceptance test: start the dev watcher, then run generation concurrently; it completes or fails within the timeout, never hangs; `kill -9` the holder and the next run recovers; two simultaneous generation passes produce one consistent manifest.

### P2 — Automatic pruning during dev/watch is unsafe with open pages and concurrent servers

Plan section: §2 line 101 ("Prune orphan outputs only after successful publication"); §4 watcher.

Verified facts: Next dev serves `public/` at request time. Already-served HTML/client bundles reference the previous content-hashed URLs. `.gitignore:17-18` shows `public/generated/*` is the established local-output pattern.

Failure scenario: a source changes → generator publishes a new manifest and prunes the old derivative → a tab still open from before the change requests the old hashed WebP and gets 404 until refresh. The same happens if a build runs against a directory a dev server is serving.

Correction: never prune automatically in watch mode. Prune only via an explicit `thumbnails:prune` command, or during a clean production build where the directory is fresh. Optionally retain orphans keyed to the last N manifests for a grace window.

Acceptance test: open a page referencing a derivative, change the source, regenerate; assert the previously served file still returns 200. Then run `thumbnails:prune` and assert it deletes exactly the files unreferenced by the current manifest.

### P2 — Content key omits toolchain/encoder version, so "deterministic" hashing can serve stale bytes behind an immutable URL

Plan section: §2 line 42–43 ("Include source bytes, profile output settings, and a generator version in the content key").

Failure scenario (hypothesis): after a `sharp`/libvips upgrade, the same source+settings encodes to different WebP bytes, but the key/URL is unchanged. Because §4 marks `/thumbnails/*` `immutable` (line 132–133), CDNs/browsers never revalidate; the "unchanged repeat run reuses conversions" and reproducibility acceptance checks fail across environments/versions.

Correction: derive the filename from a hash that includes the encoder toolchain (sharp/libvips version and exact options) or, most robustly, hash the generated output bytes and name the file by output hash. Include the Node/sharp platform version in the manifest.

Acceptance test: bump sharp’s version → keys/URLs change; two clean builds on identical versions produce byte-identical derivatives and identical manifest (excluding timestamps); swap encoder options → key changes.

### P2 — Immutable-cache rule is under-specified for preview/rolling deployments

Plan section: §4 line 132–135 ("production-only Cache-Control … Development must allow fast refresh. New source content produces a new URL.").

Verified facts: `next.config.mjs` currently has no `headers()`; Vercel previews also run with `NODE_ENV=production`, so "production-only" cannot be gated by NODE_ENV. `src/lib/uploads/direct-r2.ts:39` already uses `public, max-age=31536000, immutable` for R2 objects, so the pattern is familiar.

Failure scenario: a header rule keyed to NODE_ENV either omits previews (inconsistent) or applies to previews too (so the label is wrong); if any URL is not strictly content-addressed (P2 above), an immutable cache pins bad bytes. On a rolling production swap, old and new deployments are separate origins/filesystems, so cross-deployment pruning is not the risk — same-URL byte drift is.

Correction: apply `Cache-Control: public, max-age=31536000, immutable` to `/thumbnails/:path*` unconditionally for hashed paths (dev freshness is already guaranteed by content hashing), drop the preview/prod distinction, and verify actual response headers on a Vercel preview. Do not attempt to set headers per-file.

Acceptance test: `curl -I` a derivative on a preview and production deployment shows `immutable` with no `Set-Cookie`; changing a source produces a new URL and the old URL remains served within the same deployment.

### P2 — Serverless tracing: manifest/catalog can enter the server graph, and the `/api` exclusion is incomplete

Plan section: §4 line 137–140; plan’s assumption that excluding `public/thumbnails/**/*` is sufficient.

Verified evidence: `next.config.mjs:41-45` excludes only three specific `public` subtrees from `"/api"`; `"/api/requests"` explicitly includes `./public/pendants/**/*` (`:12-17`). The exclusions are route-keyed and do not mention thumbnails. The plan places `catalog.ts` and the manifest under `src/lib/thumbnails/`, which is importable by any server module.

Failure scenario: (a) a server component/route later imports a module that imports `StaticThumbnail` → the generated manifest (and `catalog.ts`’s imports of `lib/assets.ts`/necklace config) get traced into functions; (b) if derivatives are ever placed under a globbed `public` subtree (e.g., `public/pendants/`), the existing `outputFileTracingIncludes` would bundle them, reintroducing the >250 MB function issue.

Correction: add `./public/thumbnails/**/*` to the `"/api"` exclude and to every generation route’s exclude; keep the catalog under `scripts/` (not `src/lib`) and the manifest import client-only (a `"use client"` boundary alone does not guarantee this — verify with a trace). Since generation only needs public source paths, catalog should read `data/*.json` directly rather than `lib/assets.ts` (the legacy `lib/` layer; see P3 below).

Acceptance test: after `next build`, grep `.next/server/**/api/**` for `thumbnails`/`manifest.generated` and assert absent, while `public/pendants/**` reference assets remain present for `/api/requests`.

### P2 — Watcher can loop on its own derivative writes, and manifest writes under `src/` interact with Next recompiles

Plan section: §4 line 124–125 ("watches both registered sources and catalog dependencies. Debounce changes…").

Failure scenario (hypothesis, common failure mode): if implemented as a recursive watch of `public` or `src`, the watcher sees writes to `public/thumbnails/*` and the manifest and enqueues a new pass each time → regeneration loop. Writes to `src/lib/thumbnails/manifest.generated.json` additionally trigger Next dev recompiles.

Correction: watch an explicit allowlist of source files and catalog modules only; never watch `public/thumbnails` or the manifest; debounce and coalesce; add a guard that a derivative/manifest write cannot enqueue a pass.

Acceptance test: run a dev session through several source edits and assert pass count equals edit count; a dedicated test writes a derivative directly and asserts no generation is enqueued.

### P2/P3 — "Narrow lint rule" coverage enforcement has no lint infrastructure and is hard to enforce

Plan section: §5 line 144–145.

### P3 — Mandating movement of inline picker metadata into shared modules is a large refactor disproportionate to the goal, and couples the build to the legacy `lib/` layer

Plan section: §1 line 91–92; line 79 registers from `lib/assets.ts`.

Verified evidence: inline asset arrays live in `app/name/NameBuilder.tsx:102-107`, `app/bracelets/icedout/IcedoutBraceletBuilder.tsx:23-26`, `app/bracelets/womens/WomensBraceletBuilder.tsx:15-16`, `app/pendants/logo/LogoPendantBuilder.tsx:41-65`, `app/necklaces/necklace-options.ts:12-21`. `lib/assets.ts` imports `@/data/*.json`; `lib/styles/*` is the re-export shim layer slated for deletion per `AGENTS.md` roadmap item 2.

Failure scenario: moving configs risks touching builder behavior and prompt/compositor semantics for a purely presentational change; the generator then depends on a legacy directory that is scheduled to change, and running the script via a TS runner creates a second module-resolution surface (`@/` aliases) from `tsx`.

Correction: keep the catalog as an explicit literal list of `{ id, label, publicPath, profile }`, reading the same `data/*.json` the UI reads, without moving builder metadata. Only extract a shared data module when the build script and UI would otherwise diverge on labels/IDs. Keep catalog input free of framework/`node:*` server imports.

Acceptance test: the migration diff is limited to imports/JSX in the builders; existing unit tests (`nameBuilder.test.tsx`, bracelets/logo/picture tests) pass unchanged; `npm run thumbnails` resolves `data/*.json` directly.

Plan section: §2 line 44–46.

Verified evidence: the only SVG is `public/category-icons/grillz.svg`, referenced at `app/design/DesignEntry.tsx:16`; there are no `.gif`/`.avif` assets. `sharp` SVG rasterization requires a librsvg build and intrinsic-dimension parsing, which is nontrivial.

## Unnecessary complexity / hard-to-enforce requirements

- The full combination of writer lock + live watcher + auto-prune + `thumbnails:check` + catalog validator + lint rule is heavier than the stated goal. A build-time generator plus npm `predev`/`prebuild` plus an optional, non-pruning, opt-in watcher delivers the same user-visible outcome with far fewer failure modes.
- "Every registered ID and derivative" coverage is enforceable by a test only against a maintained inventory; it cannot be proven for unregistered/new flows. State it as a review requirement, not a machine guarantee.
- Manifest scale is not a near-term problem: the inventory here is ~70–90 source images. The union-of-widths rule (line 37–38) can inflate derivative count only when one source serves several profiles; measure and set a budget rather than designing for "at scale" prematurely.
- "Truly private files should not be in public" does not map to current reality: `data/picture-pendant-styles.json:4-7` shows the display `src` and generation `baseImage` are the same public file, and `src/lib/necklaces/config.ts` serves model references from `public/`. This should be stated as out of scope, not implied as solved.

## Recommended minimal revised architecture

1. **Catalog**: explicit literal list in `scripts/thumbnails/catalog.mjs` (or `.ts` imported only by the script) with `{ id, label?, publicPath, profile, quality? }`, reading `data/*.json` directly. No UI metadata refactor.
2. **Generator**: single `.mjs` using `sharp` only (no `tsx`). Writes `public/thumbnails/<output-hash>-<width>.webp` via temp+rename, then publishes `src/lib/thumbnails/manifest.generated.json` last by rename. Content key includes scheduler toolchain version; ideally name by output hash.
3. **Manifest**: commit it (small, deterministic). Add `thumbnails:check` that regenerates to a temp location and diffs.
4. **Invocation**: `npm run thumbnails` called from `predev` and `prebuild`; `run.sh` delegates to `npm run dev`; Playwright inherits. No separate "launcher."
5. **Watcher**: optional/opt-in, watches an explicit file allowlist, debounces, never prunes, never watches `public/thumbnails` or the manifest. v1 can omit the watcher and require `npm run thumbnails` after source edits.
6. **Locking**: per-pass lock with timeout + stale detection only.
7. **Pruning**: explicit `thumbnails:prune` only (or clean-build fresh dir).
8. **Caching**: unconditional immutable for `/thumbnails/:path*`; verify headers on a preview deployment.
9. **Tracing**: add `./public/thumbnails/**/*` to `"/api"` plus generation-route excludes; keep catalog outside the app graph; add a post-build grep assertion.
10. **Enforcement**: coverage unit test against a committed inventory + review checklist; no ESLint rule; no SVG/animation special-casing.
